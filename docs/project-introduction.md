## 0. 摘要（答辩开场 30 秒）

网站「打不开」的根因分布在 DNS、TCP、TLS、HTTP 四层，非专家往往只能截图问人或反复重试。本项目实现了一个**证据驱动的诊断 Agent**：本地大模型自主调用探测工具，把每次观测编号为 E1、E2…，在证据约束下给出分层结论和修复建议；同时搭建了一个**可复现的评测环境**——7 个真实注入的本地故障、三种提示策略、先采集后回放的对照实验。

项目的重点不是「让模型猜得更准」，而是回答一个更小、更可验证的问题：**在故障诊断这种多步、有明确 ground truth 的任务上，小模型 + 工具到底能做到什么程度，失败在哪里。**

## 1. 选题背景与问题定义

### 1.1 背景

LLM Agent 的工具调用能力在过去一年快速成熟，但「Agent 到底靠不靠谱」的评测方法仍然粗糙：多数 demo 挑成功案例展示，缺少对照、缺少失败记录、缺少可复现的观测。网络故障诊断是一个合适的试验台：

- 有**明确的分层结构**（DNS / TCP / TLS / HTTP），可以逐层验证；
- 有**可注入的 ground truth**（本机起故障，标签已知）；
- 有**确定性基线**（规则引擎），可以判断模型是否真的带来增量；
- 有**多步工具调用**，能观察 Agent 的规划与收敛。

### 1.2 问题定义

输入：一个 URL（可选症状描述）。
输出：分层诊断结论 + 证据编号 + 修复建议。
诊断空间：`normal`、`dns_failure`、`tcp_failure`、`tls_failure`、`http_error`、`slow_response`、`insufficient_evidence`。

### 1.3 研究问题

- **RQ1**：本地小模型（0.8B / 4B）能否通过工具调用达到可用的诊断准确率？
- **RQ2**：工具（tools）与领域提示（skill）各自带来多少提升？
- **RQ3**：一致性校验对最终准确率的影响有多大（首稿 vs 最终）？
- **RQ4**：主要失败模式是什么（轮次耗尽、JSON 不合规、证据不足、误判）？

## 2. 系统设计

### 2.1 架构

```text
URL ──► 目标解析与校验 ──► 探测层（DNS / TCP / TLS / HTTP）
                                   │
                                   ▼
                            证据池 E1..En（含耗时、错误类别）
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
              规则引擎（保底）              LLM Agent（自主选工具）
                    └──────────────┬──────────────┘
                                   ▼
                          一致性校验（矛盾则重写）
                                   ▼
                     报告：结论 + 证据表 + 建议 + trace
```

### 2.2 关键设计

1. **模型不能直接「看」网络**：只能通过 `check_dns` / `check_tcp` / `check_http` 三个无参数工具获取观测；工具与目标绑定，模型无法把探测引向别的主机。
2. **证据编号**：每次探测生成 E1、E2…，最终 JSON 必须引用编号；结论可回溯到具体观测。
3. **严格输出**：最终答案必须是符合 schema 的 JSON；解析失败会重试并给出 enum 候选。
4. **一致性校验**：结论必须与证据兼容（例如 HTTP 503 不能判成 `slow_response`），矛盾则打回重写；证据不足时允许 `insufficient_evidence`。
5. **两种引擎**：`rules` 提供确定性对照；`ollama` 是真实的 LLM Agent。三种模式：`baseline`（不给工具）、`tools`（给工具）、`skill`（工具 + 领域提示）。

### 2.3 探测层的工程边界

目标解析拒绝控制字符、userinfo、非 ASCII 路径；DNS 用线程 + 队列做超时；TCP 最多尝试前 3 个地址；TLS 默认校验证书；HTTP 不读响应正文、不跟随重定向。这些约束既是安全考虑，也是评测可复现性的前提。

## 3. 实验设计

### 3.1 案例

7 个案例，其中 5 个由本机真实故障注入（DNS 失败、TCP 拒绝、TLS 握手失败、HTTP 503、慢响应），2 个为合成夹具（DNS 失败、证据不足）。每个案例有唯一期望结论和「决定性工具」集合。

### 3.2 变量与流程

- 自变量：引擎（rules / ollama）× 模式（baseline / tools / skill）；
- 控制：同一案例先真实采集一次观测，再回放给三组，保证三组看到完全相同的输入；
- 记录：每次工具调用、每版草稿、每次校验失败、最终结论、耗时；
- 可追溯：manifest 记录源码 sha256，trace 逐轮落盘。

### 3.3 指标

| 指标 | 定义 |
|---|---|
| 首稿准确率 | 第一个结构合法的结论是否等于期望 |
| 最终准确率 | 经过一致性校验后的结论是否等于期望 |
| 任务成功率 | 结论正确 **且** 引用了决定性证据 |
| 证据覆盖率 | 引用的决定性工具 / 该案例应有的决定性工具 |
| 有效工具调用率 | 工具名、参数、前置条件都有效的调用 / 总调用 |
| 执行失败 | 轮次耗尽、解析失败、HTTP 错误等 |
| 耗时 | 单案例端到端时间 |

## 4. 当前结果

### 4.1 规则引擎

7/7 正确，0 失败。这是「已知案例上的确定性上限」，不是 LLM 的成绩。

### 4.2 4B 模型（`qwen3.5:4b-q4_K_M`，7 案例 × 3 组，各 1 次）

| 组 | 首稿 | 最终 | 任务成功 | 证据覆盖 | 平均耗时 |
|---|---|---|---|---|---|
| baseline | 85.7% | 100% | 100% | 90.5% | 29.94s |
| tools | 85.7% | 100% | 85.7% | 95.2% | 45.45s |
| skill | 100% | 100% | 100% | 100% | 65.72s |

初步观察：

- **工具与 Skill 的提升主要体现在首稿**（85.7% → 100%），最终准确率被一致性校验拉平；
- Skill 组最慢（65.72s），存在明显的「质量—时延」权衡；
- tools 组的任务成功率反而低于 baseline，原因是「证据不足」案例没有引用决定性证据——结论对，但论证不完整。

### 4.3 0.8B 模型

3 个案例的小样本测试中，baseline 与 skill 各出现 1 次 8 轮耗尽、8 次校验失败；tools 最终 100% 但任务成功率只有 66.7%。说明 0.8B 在工具调用与格式遵循上尚不稳定，不适合作为主模型。

### 4.4 必须说明的现状

上述 4B 数字是**单次运行、7 个案例**，且该模型当前不在本机模型仓库中；`verified-live-model` 目录里还有一份加护栏之前的旧结果（503 被判成慢响应），不能引用。答辩前必须用可用模型重跑，并标注运行次数。

## 5. 讨论：有效性威胁

这一节是答辩最容易被追问的地方，主动讲比被问出来好。

### 5.1 构念效度（Construct Validity）

- 7 个案例不能代表真实故障分布；实验室注入的故障比现实「干净」，缺少 CDN、代理、IPv6、偶发丢包等干扰；
- 2 个案例是合成夹具，不是真实探测；
- 「证据覆盖率」只衡量是否引用决定性工具，不衡量推理质量。

### 5.2 内部效度（Internal Validity）

- **回放不校验探测前置顺序**：实测有案例跳过 TCP 仍拿到 HTTP 观测，并被记为有效调用，会高估「有效工具调用率」；这是已知缺陷，修复后需重跑；
- 每个配置只跑 1 次，温度虽为 0，但模型输出仍有波动；
- 提示词、工具描述、校验规则由作者设计，可能存在「为案例调参」的风险；
- 三组共享同一套校验规则，因此「最终准确率」的差异被压缩，不能据此判断模型原始能力。

### 5.3 外部效度（External Validity）

- 单机、单网络视角；真实故障常与地域、路径相关；
- 只测本地 Ollama 模型（0.8B / 4B），不能外推到更大模型或闭源 API；
- 本机 TLS 信任链存在异常：`example.org` / `example.com` 证书校验失败，`baidu.com` 正常；当前会把这类环境问题报成 TLS 故障，需要在报告中标注「本机视角」。

### 5.4 结论效度（Conclusion Validity）

- n=7，无重复，无置信区间；85.7% 与 100% 只差 1 个案例，**不能声称 Skill 显著更优**；
- 规则引擎在同样的 7 个案例上 100%，说明「分类」本身可被规则覆盖；LLM 的增量应表述为「解释、长尾、多语言」，而不是「更准」。

## 6. 局限与未来工作

**局限**：单点探测、案例少、模型小、无多地域、无 JS 渲染、无登录态；TLS 归因偏粗；回放前置校验缺失。

**未来工作**：
1. 修复回放前置校验，补「跳过 TCP 应返回 not_ready」的测试；
2. 拆分 `SSLCertVerificationError` 与其他 `ssl.SSLError`，区分配置问题与握手问题；
3. 扩到 12–15 个案例，每个配置重复 3 次，报告均值与区间；
4. 增加第二个网络视角（另一台机器/云主机），观察单点误判率；
5. 对比一个更大的本地模型（7B/8B），验证「模型规模—诊断质量」曲线。

### 7.3 预计被问的问题

**Q1：规则已经 100% 了，为什么还要 LLM？**
规则在 7 个已知案例上是上限，不是现实；LLM 的价值在解释、未知长尾、多语言和「把观测翻译成行动」。项目保留规则作为对照，不宣称 LLM 更准。

**Q2：7 个案例能说明什么？**
这是一次 pilot study，用于暴露失败模式和验证评测流程；我们逐案例报告，不做显著性声明。扩案例与重复运行在未来工作里。

**Q3：回放公平吗？**
同一份观测回放给三组，输入完全一致；但当前回放缺少前置顺序校验，会高估有效调用率——这是已知缺陷，修复后重跑，数字会更新。

**Q4：为什么首稿 85.7%、最终 100%？**
一致性校验会把与证据矛盾的结论打回重写；我们特意分开报告，避免把「纠正后的成绩」当成模型能力。

**Q5：0.8B 为什么失败？**
8 轮内无法稳定产出合规 JSON，或反复调用同一工具；说明工具调用存在模型规模门槛。

**Q6：证据覆盖率怎么算？**
引用的决定性工具数 / 该案例应有的决定性工具数；它衡量「论证是否完整」，不衡量推理是否正确。

**Q7：TLS 误报怎么办？**
本机信任链异常导致部分 HTTPS 站点校验失败；将区分证书校验失败与握手失败，并在报告里标注「本机视角」，避免把环境问题当成站点故障。

**Q8：创新点是什么？**
不是新算法，而是两点工程与方法贡献：证据约束的 Agent 设计（结论必须可回溯），以及可复现的故障诊断评测（真实注入 + 回放 + 首稿/最终分离）。
